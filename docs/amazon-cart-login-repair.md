# Cart cleanup and automatic sign-in

The previous Delete resolver counted hidden responsive copies alongside the visible button, rejecting an otherwise usable cart row. Cleanup now waits for one usable Delete control in each uniquely identified unrelated active-cart row. It supports native submit controls, accessible icon labels and nested wrappers around the same button. Hidden/disabled copies are excluded. Two distinct usable actions still require review. Each deletion must be acknowledged before proceeding; a lost acknowledgement never triggers another click. Target identity and exact quantity remain mandatory.

Amazon's `submit.delete-active.<item-id>` name and `data-action="delete-active"` are explicitly supported, alongside the accessible Delete label. A regression fixture preserves the user-supplied input markup and verifies three unrelated active items are removed across row rerenders while the target quantity and saved-for-later entries remain unchanged. Separate cases verify matching by name and action independently of the label.

The remaining ambiguity was reproduced from a failed attempt's saved browser trace: a quantity-one row exposes both a stepper trash button labelled Delete (`a-stepper-decrement`) and the dedicated `delete-active` input. The resolver now excludes quantity-stepper controls and their descendants before counting actions. It retains semantic-label support for older layouts and rejects two distinct non-stepper Delete actions. It never substitutes a quantity decrement when the dedicated action is missing.

`tests/fixtures/amazon_cart_stepper_delete.html` reconstructs the observed control hierarchy with synthetic items only. The new regression failed with the reported error before the fix. Chrome DevTools MCP inspected the fixture using the production resolver; Playwright MCP clicked its selected controls and verified that only the two unrelated active items were removed, across rerenders, with the target quantity and saved-for-later entries preserved. Additional cases cover delayed availability, a stepper without a Delete action, and two genuine Delete actions. The MCP sessions inspected the reconstruction, not the live account tab; no live cart changes or purchases were made.

Stepper-fix regression command: `python -m pytest tests/test_amazon_cart_login_repair.py tests/test_amazon_cart_speed.py -k "delete or reconcile or uncertain or target_removed" -q --disable-warnings --maxfail=1`. Result: 30 passed, 13 deselected in 42.40 seconds. This is controlled test runtime, not live Amazon latency.

The subsequent removal timeout had a separate cause, confirmed through read-only CDP inspection of the affected live cart: Amazon retains the deleted row's ASIN and quantity on a visible `.sc-list-item-optimistic-updates[data-removed="true"]` removal notice. The old `cart_removed` predicate returned false on that page; the corrected predicate returned true. Cart reads, readiness predicates and cart control locators now exclude these notices and their descendants. Busy-state and interruption checks remain in force. Cleanup returns its verified current rows, so quantity normalization uses the post-cleanup quantity and checkout reuses the same read instead of adding another snapshot.

The synthetic `amazon_cart_removed_notice.html` fixture reproduced the exact timeout before the fix. Its regression tests cover immediate/delayed removal notices, quantity changes during cleanup, quantity correction through the stepper, checkout navigation, missing acknowledgement, a busy cart, sign-in interruption, removed target notices and readding an ASIN beside its old notice. Playwright MCP verified two deletions, quantity changes from three to one and checkout navigation using the production state predicates. No real cart mutation or order was performed during validation.

Removal-notice regression command: `python -m pytest tests/test_amazon_cart_removed.py tests/test_amazon_cart_speed.py tests/test_amazon_states.py tests/test_amazon_cart_login_repair.py -k "not automatically_signs_in and not task_recovers and not foreign_signin" -q --tb=short`. Result: 51 passed, 11 deselected in 73.10 seconds. These cover the changed cart/state paths and existing submission/cancellation guards; credential-entry and task-runner cases excluded by this command were not changed.

Product pages can show a signed-out header without a conventional `/ap/signin` link. Startup now uses Amazon's protected order-history route when that link is unavailable or unsafe, allowing Amazon to provide its own sign-in page. It supports separate and combined credential forms, `ap_email` and `ap_email_login`, and delayed form hydration. Saved account credentials are entered with the existing bounded paced mouse/keyboard controller, independent of checkout pacing. An unchanged prefilled email is retained. Page transitions remain state-driven; pacing applies to input only.

Credential entry and form destinations must stay on the account's HTTPS Amazon region. Rejected credentials are not resubmitted in a loop. CAPTCHA, unsupported verification and missing credentials pause for review; existing account-owned OTP handling remains available. Successful verification saves the session and returns to the requested product automatically. A fresh account offer check detects an explicitly signed-out header; anonymous inventory scanning continues to work independently.

When the original task runner encounters sign-in after dispatching a cart action, recovery reconciles the existing cart instead of replaying Add or Buy Now. A missing target after an uncertain add pauses rather than assuming the add failed. An existing submission intent still prohibits all purchase retries. Compatibility plans retain their durable uncertain-outcome handling.

Validation uses intercepted Amazon page fixtures and simulated task execution. Coverage includes hidden/disabled controls, accessible icons, delayed and nested controls, genuine ambiguity, missing target, lost mutation acknowledgement, automatic login, trusted keyboard/pointer events, delayed/combined forms, foreign destinations, rejected credentials, challenges, session saving, anonymous stock inspection and continuation without Resume. No real transactions are placed, and no live retailer latency or universal layout-coverage claim is made.

Validation result: 162 distinct cases passed across the regression run and focused reruns; one optional native-browser test was skipped because its binary was unavailable. The regression run initially exposed an incorrect field name in a new assertion (`stock_status` instead of `availability_status`); the assertion was corrected and rerun successfully. The final runner changes also passed all 25 checkout/monitor tests and both single-/multiple-product recovery cases.
