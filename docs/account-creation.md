# Account creation

Accounts → Account creation sits beside Sessions & relationships. New account asks for name, email, password, and optional Amazon region, connection, IMAP mailbox and CAPTCHA provider. Save & start signup creates one encrypted account record, opens Amazon home, hovers Account & Lists and clicks the observed Start here link with its original parameters. Email-first and full-registration forms use paced input. Existing Amazon records can start signup from their row if credentials are present and no session is saved.

A linked IMAP mailbox supplies a fresh recipient/sender-matched email code, using existing read-only retrieval and replay receipts. Automatic code retrieval waits at most 45 seconds and submits at most once per signup run. Assigned image providers use the existing ImageToText integration for recognized image CAPTCHAs; only the challenge image is sent. One provider attempt is recorded before requesting a solve, preventing repeated charges after uncertainty. Unsupported challenge types, failed services and phone verification go to the manual harvester queue. Solving in the same browser resumes from observed page state. The existing sign-in watcher verifies the session through the account page before saving it; showing a signup page or submitting the form never marks the account signed in. Show browser, Save session and Close browser use existing account-session actions. US, UK and Canada use the regional workflow; only the US entry page was inspected live. Other retailer signup adapters are not implemented.

The encrypted `account_creation` journal stores account references, timestamps, status and submission-intent flags, never copied credentials or page content. Intent is saved before email-claim, the intermediate Proceed action, registration and verification dispatch. A submitted or uncertain attempt cannot automatically submit again, including after restart; Open sign-in provides reconciliation. Editing unrelated account options preserves the journal. Retailer cooldowns prevent fresh signup requests until their deadline.

Signup uses the same account action lock, account browser registry and shared browser semaphore as existing task/browsing work. The browser retains its slot through verification and releases it after owned browser teardown. Startup and initial registration are bounded to 90 seconds; verification observes at most 12 transitions within 30 minutes. Closing the browser cancels the verification owner. No second scheduling loop or bulk signup is added. The existing account browser profile is allocated before signup and retained afterward; its account-specific seed is stable and distinct from other accounts, and existing explicit fingerprint settings remain authoritative.

If a known selector changes, a process-local MCP client asks the account-owned recovery server to inspect current control metadata through CDP. Only recognized signup field/control roles can be selected; missing, ambiguous and foreign-origin results stop for review. Recovery is bounded to five seconds per lookup and does not call a model, expose secrets or general JavaScript tools, rewrite source, bypass verification, or repeat a possibly submitted action. It can handle recognized layout variations, not every future retailer redesign.

The “Looks like you're new to Amazon” interstitial is an explicit signup state. Its “Proceed to create an account” control is recognized using its accessible label, including `aria-labelledby`, without depending on an element ID. Startup waits for actionable controls after navigation rather than assuming DOMContentLoaded means the form is ready. The verification watcher also resumes when this intermediate state appears later. An ambiguous control or a previously dispatched Proceed action requires review; the email claim is not replayed. Controlled regression coverage: `python -m pytest tests/test_signup_proceed.py tests/test_account_creation.py tests/test_signup_verification.py tests/test_infrastructure.py -q`.

Gmail configuration and troubleshooting: [IMAP setup](imap-setup.md).

Email-code recovery recognizes the visible label “Enter security code”, common OTP field names and the plain “Verify” button. State detection and MCP/CDP control recovery share this classification, including delayed/disabled controls becoming ready. The field and button must be unique and belong to the same regional verification form before an IMAP message is consumed. A replaced page/form cannot receive a retrieved code. Submission intent remains durable and is saved before clicking Verify. Missing mailbox assignments, disabled automatic OTP, ambiguous controls and already-submitted codes have explicit email statuses instead of the generic verification message. Automatic OTP failures use `Automatic email verification paused` and do not enqueue a manual email-code request. Control changes resume detection; an already-submitted code is never replayed. Manual email-code requests are reserved for disabled automatic OTP or no linked mailbox. Each account row shows its assigned mailbox or manual code entry. Forwarded mail still requires the signup recipient to remain in To, Delivered-To or X-Original-To; a tested mailbox alone is not an account assignment. The parser accepts Amazon's “One Time Password (OTP):” wording and HTML entities while preserving sender, recipient, freshness and replay checks.
