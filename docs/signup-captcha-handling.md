# Signup CAPTCHA handling

Account creation inspects visible controls and up to 32 visible browser frames, including nested cross-origin frames. The detector recognizes image CAPTCHA, Arkose/FunCaptcha, reCAPTCHA v2/Enterprise, hCaptcha, Turnstile, GeeTest, AWS WAF CAPTCHA, DataDome, Friendly Captcha, Tencent and MTCaptcha markers. Unrecognized security-puzzle headings or challenge frames produce a generic CAPTCHA prompt. Hidden frames and script tags alone do not trigger a challenge. Marker-based detection cannot guarantee recognition of every future retailer variant or invisible score-based check.

Manual selection creates a named entry in Tools → Verification → Manual harvester queue and sets the account status to **CAPTCHA — user input required**. Open signup browser returns to the same account browser. The watcher detects completion and resumes the existing signup; it does not restart registration.

Automatic selection uses the account's assigned provider. Current adapters:

| Provider | Automatic signup adapters |
| --- | --- |
| 2Captcha | Image text; Arkose/FunCaptcha, reCAPTCHA v2 and standalone Turnstile token forms |
| CapMonster | Image text; Arkose/FunCaptcha, reCAPTCHA v2 and standalone Turnstile token forms |
| Anti-Captcha / CapSolver | Existing image-to-text adapter |
| Manual / FlareSolverr | Manual challenge completion; FlareSolverr remains a separate diagnostic |

Provider capability is not the same as a supported retailer integration. Token solves require a unique retailer-owned response field, current public key and a separate verification form with one submit control. Amazon's observed CVF form is a specific exception to the visible-button requirement: `cvf-aamation-challenge-form` owns the hidden `cvf_aamation_response_token` input and posts to `/ap/cvf/verify`. Its public key and blob come from the current `aacb-arkose-frame` inside the same-origin verification wrapper. The provider token is delivered through the observed Amazon wrapper callback to Amazon's `/aaut/verify/` exchange. Amazon validates it and submits its own session token through the existing CVF form, preserving its CSRF and context fields. A raw provider token must never be placed in the final CVF field. See [the bridge repair](cvf-bridge-repair.md) for live validation. Frame/document replacement, duplicate fields, changed destinations and an already-populated response stop delivery. Registration/password forms are not resubmitted. Other embedded puzzles with only an opaque callback or message interface require manual completion. There is no general callback discovery, forged completion message, or cookie replacement. hCaptcha, GeeTest, Enterprise variants, AWS WAF, DataDome and the remaining detected families currently request manual completion even if a provider advertises support for them.

CapMonster Arkose requires the account browser's actual proxy, including its credentials when configured. The in-memory browser connection is used rather than choosing another proxy. If no proxy or required challenge parameters are available, the app requests manual completion before creating a paid task. Only an assigned service receives the CAPTCHA image or task parameters (page URL, public key, challenge data, and applicable proxy details); account credentials and session cookies are not sent. Tokens, blobs and proxy credentials are not written to the account-creation journal or queue.

On 2026-10-11, a user-requested direct `FunCaptchaTask` request with proxy fields omitted was rejected by CapMonster with `ERROR_PROXY_MISSING`; no token was returned or submitted. The configured key passed a balance check. The original manual fallback was earlier than the provider call because the CVF response field was unrecognized. The adapter now recognizes that shape and explains the missing browser proxy before making a paid request. [CapMonster Interceptor](https://docs.capmonster.cloud/docs/external-services/) redirects other solver APIs to CapMonster; it does not supply a matching browser proxy. A rejected or interrupted direct attempt remains recorded and is not retried automatically.

CapMonster documents dynamic Arkose data and warns that a loaded challenge may have consumed its blob. These fixtures validate form recognition, request construction and safe delivery, not fresh-blob acquisition or live Amazon acceptance. The existing open puzzle has not been solved by this change. A matching-proxy live integration still needs validation with fresh challenge data; an expired/consumed challenge must not trigger a registration replay.

An automatic attempt is recorded before creating a paid task. Each challenge is attempted once. One bounded registration retry is permitted after an internal error only when the saved identifier is reconciled; a new challenge in that resumed registration can receive its own solve. Provider errors, deadlines, changed pages, replacement challenges, unsupported forms and mismatched solver/browser user agents cause manual fallback. Receiving a solver token alone does not mark the CAPTCHA accepted or the account signed in. The current form is submitted once and the existing session verifier remains authoritative. The browser identity is not changed to fit a solver result.

Validation uses controlled Patchright/Playwright pages and mocked provider responses. It covers frame nesting, hidden challenges, manual routing, token forms, provider-specific task types, proxy propagation, changed challenges, missing parameters, foreign destinations, cancellation, one-request behavior, account isolation and secret redaction. No real CAPTCHA service was charged, and no live registration or purchase was submitted. Live Amazon callback-only puzzle compatibility is not established by these fixtures.

CVF regression command: `python -m pytest -q tests/test_signup_cvf_captcha.py tests/test_signup_challenges.py tests/test_signup_verification.py tests/test_account_creation.py tests/test_signup_email_code.py`. The CVF fixture reproduces the hidden response field, absent submit button, nested frame and action-shadowing input with synthetic values. It checks one native submission, preservation of CSRF/context fields, cancellation/restart, account isolation, no-proxy preflight, provider failure, replaced frames/forms and changed destinations. The separate live direct-request rejection above is not part of development tests.

CVF validation result: **96 passed** in **170.21 s**, with the existing Starlette/httpx deprecation warning. Desktop (1440px) and narrow (390px) account-creation CAPTCHA screenshots were visually inspected. `python scripts/benchmark_signup_cvf.py` reproduces the controlled preparation measurement: 20 samples after 5 warmups, median **74.515 ms**, p95 **85.541 ms**, maximum **92.284 ms**. This measures local frame/form inspection plus browser protocol overhead only; it does not measure provider time, live retailer latency or a before/after speedup. Healthy non-CAPTCHA actions do not enter this adapter.

On 2026-10-11, a second live incident showed the inner Arkose iframe was not ready when preparation ran. The same open page later passed preparation without a reload. The watcher previously compared the document and CAPTCHA family, so it remained in manual mode when only the nested frame became ready. Preparation now waits up to ten seconds for a unique, visible wrapper and inner frame with valid key/blob parameters. The watcher observes the same readiness condition and resumes an unpaid attempt when loading finishes after that deadline. The original response field is revalidated after waiting. Paid attempts remain durable and are never repeated automatically.

Readiness fixtures cover immediate availability, delayed insertion, expansion from zero dimensions, delayed parameters, missing and ambiguous frames, cancellation and form replacement. An integration fixture keeps the same document and Arkose classification while the frame expands after the initial timeout; it verifies no paid request before readiness and exactly one solve/submission afterward. Controlled preparation timing after this change: 20 samples after five warmups, median **69.944 ms**, p95 **86.792 ms**, maximum **95.743 ms**. Compared with the earlier local measurement this shows no material preparation regression, not an established speedup; browser scheduling and concurrent tests affect these small samples.

The user-authorized live attempt on the current Amazon challenge used the configured browser proxy and returned **ERROR_CAPTCHA_UNSOLVABLE**. No token was returned or submitted, and the durable paid-attempt flag remains set. A separate public reCAPTCHA demo succeeded through the same proxy; that does not establish Arkose compatibility. The new readiness predicate also passed read-only against the still-open Amazon page. The cause of the provider rejection is unconfirmed, and the readiness fix does not claim to resolve it. No account registration or purchase was replayed.

Readiness validation result: **104 passed** in **177.95 s** using the regression command above, with the existing Starlette/httpx warning. The delayed-frame integration also passed independently after synchronizing its state-inspection assertion with the mocked solver. Desktop (1440px) and narrow (390px) CAPTCHA status screenshots were inspected again. Source review confirmed that only pre-solve preparation and read-only state observation changed; the durable paid-request and one-submission boundaries remain intact.
