# Mouse and keyboard library review — 2026-10-06

The current application uses asynchronous Python Patchright, owns each account's context, and depends on locator actionability, cancellation, exact field values, and final order revalidation. Those requirements matter more than a library's marketing claim of undetectability. This review does not establish human equivalence for any candidate.

| Candidate | Fit and evidence | Decision |
|---|---|---|
| [HumanCursor-Playwright 0.1.1](https://pypi.org/project/humancursor-playwright/) | Async Python movement; accepts an existing page. Wheel source uses duck typing compatible with Patchright. Depends on Playwright, NumPy and PyTweening; packaged license is MIT. Published repository URLs still contain `yourusername`. `click_on()` calls coordinate mouse input after movement, without retaining locator actionability checks; it also ignores a false return from `move_to()`. No typing model. | Closest mouse-only integration candidate, but unsuitable as a direct click replacement. Movement-only evaluation could be isolated behind the existing controller; no measured advantage yet justifies adding it. |
| [Humanization-Playwright 0.1.2](https://github.com/saksham-personal/humanization-playwright) | Async Python/Patchright, MIT, movement and keyboard helpers. Source calls `page.mouse.click()` and focuses only before its typing loop, then uses page-wide keyboard presses. Own launch helper and Loguru configuration. Typing remains sequential with randomized hold and inter-key waits. | Adds overlapping functionality and integration work. Does not establish a fix for the previously measured distribution gaps. Keep current context ownership and checks. |
| [HumanTyping](https://github.com/Lax3n/HumanTyping) | MIT, Python async locator interface, QWERTY support, word/bigram delays and modeled errors/corrections. Inspected revision `db142362206f46b9a9d0c2687c88ab4105b9b9d1`. Async adapter sleeps between actions then calls `locator.press(char)` without a hold delay; it does not independently schedule keydown/keyup or verify the final field value. | Interesting keyboard research candidate. Its model does not automatically improve actual key-hold or overlap behavior. Error injection needs separate exact-value and cancellation validation before use in credentials, quantities or payment fields. Not incorporated. |
| [human_typer](https://github.com/UnMars/human_typer) | Python typing helpers with Playwright/Selenium and desktop keyboard options. Inspected implementation uses synchronous element calls and blocking `sleep`; supports deliberate mistakes and corrections. | Poor fit for the existing asynchronous account workers without an adapter. Desktop keyboard output also operates outside account browser isolation. |
| [Ghost Cursor](https://github.com/Xetera/ghost-cursor) | MIT, Node/Puppeteer movement/path generation. | Useful reference, but introduces a language/browser integration boundary and supplies no keyboard model. |
| [CloverLabsAI/human-cursor](https://github.com/CloverLabsAI/human-cursor) | ISC, TypeScript/Playwright movement implementation. README typing example uses a fixed `keyboard.type` delay. | More direct for a TypeScript application; not an efficient replacement for this Python controller or a keyboard realism solution. |
| [HumanCursor](https://github.com/riflosnake/HumanCursor) | Python Selenium WebCursor and desktop SystemCursor variants. | Neither interface directly matches async Patchright. Desktop input would affect the user's actual pointer and does not provide independent account cursors. |

The two PyPI wheels were downloaded and inspected as ZIP archives, without installing or importing them. Their SHA-256 digests matched PyPI metadata:

- HumanCursor-Playwright: `ace5403d586f1f68d7b3dacc3f163b6352711a8df46a67c52900df735cda6eed`
- Humanization-Playwright: `9d2a476c96f1276c88468245f10215582ec727916baf9a64729fc24480b71d42`

Reviewed source, metadata and file hashes are in `artifacts/behavior-web-2026-10-06/library-review/`. No dependency or production interaction behavior changed for this review. None of the inspected documentation supplied an independently validated comparison showing better results on this application's tasks. Native Playwright APIs already expose the [keyboard primitives](https://playwright.dev/python/docs/api/class-keyboard) needed for controlled input experiments; adopting a package still requires measuring the browser events it actually produces.
