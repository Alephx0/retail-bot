# Automatic Amazon Offer ID discovery

Leave Offer ID blank in the group's Monitoring tab. Product inspection automatically reads the active Add to Cart form's `offerListingID`, `OfferListingId.1`, or `offeringID.1` alongside its ASIN. A manually supplied ID remains an exact-match filter; discovery does not overwrite group settings. Product observations indicate whether an Offer ID was found, and Copy input includes it.

`Use Offer ID when found`, directly below Offer ID, defaults on to preserve existing behavior. Off means saved group and per-product IDs are ignored for matching, discovered tokens are not bound to Add to Cart/Buy Now, and the additional offer-token cart/checkout checks are not used. IDs remain saved and can still be discovered, displayed and notified. Native Amazon forms may still send their own offer fields; this switch controls the app's offer-specific handling, not Amazon's form contents. Re-enabling restores saved filters. Stop the group's tasks before saving; each run uses the captured choice. No migration rewrites existing records.

With Direct Offer ID carting disabled, this is token validation around a native click, not a faster ATC request implementation. [Refract's Amazon guide](https://help.refractbot.com/modules/amazon) attributes its OID speed claim to targeting the offer and bypassing traditional monitoring. It also says different OID strings can represent the same underlying offer. This app cannot infer equivalence from opaque strings: its explicit ID filter and row checks remain conservative exact comparisons. Both Use Offer ID modes still verify the assigned account's product page, preserving polling, cooldowns and existing purchase checks. Direct Offer ID carting is a separate opt-in described below. No speedup comparable to that claim has been established.

Product observations now also save the assigned account's inspection, labelled `Account offer` with the account name, separately from `Inventory monitor` results. One record per task/product is refreshed; anonymous stock never supplies account purchase authorization. A blank setting stays blank even when an ID is discovered and used. When pinning a manual ID, supply the field's value rather than its HTML markup.

The task row also shows whether its last account check found an ID. Task details displays that observation's ASIN, timestamp and read-only ID with Copy Offer ID. These historical observations never authorize future cart actions. `Notify when Offer ID Found` now covers discoveries in the assigned account as well as the monitor, with the existing per-run token deduplication and asynchronous notification queue. Notification settings remain authoritative; raw tokens are not included in notifications.

## Offer use during cart and checkout

Each run clears its previous offer-use status. A discovered token is rechecked against the native purchase form after input preparation, including standard input and Buy Now. Task details records the exact token, ASIN, action, timestamp and separate form/cart/checkout results. A dispatched native click is not claimed as server acceptance; interrupted dispatch is recorded as uncertain and is never replayed.

After cart reconciliation, before checkout navigation, during checkout review and again before automatic submission, the adapter checks the token when the uniquely identified target row exposes it. Supported evidence is the row's `data-offer-id`, `data-offer-listing-id`, `data-offering-id`, or its own named offer input. Conflicting evidence stops further automation without another Add or order attempt. Evidence that matched earlier and then disappears also stops. Unrelated products, saved items and global offer inputs cannot establish a match.

When Amazon exposes no row token, the UI explicitly reports `Not exposed by Amazon; exact ID unverified`. Existing product, quantity, seller, condition and price checks continue; this is not an exact offer-acceptance guarantee. Modern checkout layouts without an identifiable offer row retain that limitation. Manual browser-review tasks do not claim checkout validation for actions the user completes outside the automated review. Fresh checkout snapshots persist the offer evidence alongside the durable submission intent; historical UI data never authorizes a mutation.

The reported bananas failure was a pre-cart filter rejection, not a changed cart: the saved account inspection discovered a token different from the supplied token. The later unfiltered run verified its cart. Error messages now distinguish a differing discovered token from an unreadable token and explicitly say that no cart action was sent. This change does not silently replace a manually pinned offer or introduce direct HTTP checkout. The account observation is recorded before the eligibility decision so both accepted and rejected offers can be inspected.

Discovery runs inside the existing product snapshot, with no extra discovery navigation or retailer API credentials. It reads current field values and rejects conflicting tokens, ambiguous product identity, a different ASIN, and cross-origin form destinations. It ignores unrelated fields elsewhere on the page. It discovers the exposed featured offer, not an exhaustive list of hidden/alternative offers. The token is evidence from the page, not a guarantee Amazon will accept it at checkout.

Anonymous monitors can record the token as an observation. Only the assigned account's fresh product inspection can bind a token to carting. The binding belongs to that page, expires after 15 seconds, is cleared at each inspection, and is consumed once. Carting identifies the corresponding native control and verifies the same token/ASIN again after paced movement. Missing IDs retain normal control resolution. Changed/expired discovered offers stop before Add to Cart. Normal carting preserves Amazon's native click path. The optional shortcut posts the supported observed form once; it never guesses a standalone cart URL or replays an uncertain mutation.

Price, seller, condition, stock, quantity and final order checks remain authoritative. HumanTyping, retailer polling and cooldowns remain in use. Normal carting retains native actionability, mouse pacing and click dwell; direct form carting skips pointer movement and click dwell for Add to Cart only. Buy Now retains its existing separate flow.

## Direct Offer ID carting

The group Monitoring tab has a separate `Direct Offer ID carting` preference (default off). It requires `Use Offer ID when found`. It is enabled for the user's Test group after local validation; other groups retain their saved values. The choice is frozen at run startup and Buy Now retains its normal path.

On supported forms this path posts directly from the task browser to the observed same-origin HTTPS `/gp/product/handle-buy-box` form action. It uses the freshly inspected account-page token and successful fields, including CSRF/session fields, duplicate fields, selected quantity and the Add to Cart submitter. It excludes known Buy Now-only container fields. Percent-encoded tokens are preserved as field values and serialized by the browser. It does not generate or substitute an unverified OID or send an arbitrary endpoint request.

One browser operation resolves the unique control, captures the acknowledgment baseline, validates current fields and submits the form. It requires an exact product/token match, consistent quantity and nested item fields, one nonempty CSRF value, POST/urlencoded/self-target semantics, form validity and no visible modal. Requested quantities are serialized directly from supported dropdown options without triggering dropdown/change handlers. Unsupported forms fall back to one ordinary click **before** any POST. There is no separate form preflight round trip; checks and posting run in the same JavaScript turn, and a document marker prevents repeating the same form. A changed form stops before dispatch. Cancellation, lost acknowledgement, network errors, rate limits or later verification failures never trigger a click fallback or another Add. Browser response handling retains Retry-After and stops on uncertainty. Existing cart cleanup, exact quantities, final price/seller checks and durable order submission remain authoritative.

The shortcut skips pointer travel, click dwell and click/submit handlers; it does not skip account eligibility or read-only stock checks and does not perform repeated cart requests. It waits for navigation commitment and observable acknowledgment, without waiting for unrelated deferred scripts or DOMContentLoaded on the POST response. It reuses a cart redirect or opens the cart once. `Task details -> Offer validation` identifies `Direct Offer ID carting`, native fallback when unsupported, and separate form/cart/checkout evidence. A completed POST navigation alone is not proof Amazon accepted the offer. The bounded stage `Prepare and dispatch direct Offer ID` is nested inside the direct POST stage; the latter also includes the navigation response wait, so these timings must not be added together.

`python -m pytest -q tests/test_offer_shortcut.py` checks exact serialization, duplicate/disabled/checkbox fields, quantities, delayed responses, changed forms, unsafe Buy Now flags, unsupported-form fallback, dispatch markers, rate limits, lost acknowledgement and cancellation. Tests use intercepted product/POST/cart fixtures; no real purchase or real-account cart mutation is made to validate this route. Live Amazon form/server compatibility is not established by these fixtures.

`python scripts/benchmark_offer_shortcut.py` measures 12 alternating samples per route/input mode after two warmups, with initial product inspection excluded. Local standard native/direct cart medians were **157.47/126.61 ms**, p95 **173.56/136.50 ms**. Paced native/direct medians were **886.62/130.06 ms**, p95 **974.43/138.21 ms**. The larger paced difference comes from omitted input delays. The measurement includes intercepted POST acknowledgement, cart navigation and verification; it excludes live network, account sign-in, product inspection, task persistence, checkout and order submission. It does not establish equivalent live retailer speed or Refract performance. Raw samples: `artifacts/offer-shortcut/benchmark.json`.

## Validation and performance

### Optional endpoint request

`Send directly to endpoint` is an additional group Monitoring preference, off by default. It requires both `Use Offer ID when found` and `Direct Offer ID carting`. Turning off either parent preference disables its effect without erasing the saved choice. Partial group edits preserve it, each task freezes it at startup, and anonymous monitors never send cart requests. Buy Now retains its existing route.

On a supported form it sends one same-origin browser `fetch` POST to the observed `/gp/product/handle-buy-box` action. The task browser supplies its own cookies, proxy and current form/CSRF fields. The request preserves the exact token, repeated fields and selected quantity. It does not navigate to or render the Add to Cart response, execute its scripts, or load its images/frames. The response is read with a 15-second deadline and 2 MiB cap, parsed in a detached template, and reduced to acknowledgment/error evidence. The existing cart is then opened once for product, quantity and exposed Offer ID verification.

Redirects are not followed: in particular a 307 cannot replay the POST at another destination. Because browser fetch hides a manual redirect's response details, this result is labelled unconfirmed and only the known same-origin cart is inspected. It must already contain exactly the requested target and quantity; ambiguous contents, extra items or wrong quantities stop before any cleanup or adjustment. HTTP errors, full Retry-After, sign-in/challenge responses, missing acknowledgments, timeouts and cancellation preserve uncertain outcomes without a second Add or click fallback. Unsupported form shapes may use the existing native fallback only before dispatch. Task details labels the route `Direct Offer ID endpoint request`, and distinguishes response acknowledgment from redirect and cart verification.

This removes **ATC response rendering**, not initial account/product discovery. The application still needs current account eligibility and page-issued session fields; it does not invent a separate public ASIN/OID-only API, bypass price/seller limits, or poll a cart-mutating endpoint for stock. [PanAIO's Amazon guide](https://docs.panaio.com/sites/amazon) describes an OID fast mode but does not publish the request contract or an almost-instant latency measurement. Its claims are not a benchmark for this implementation. Fetch redirect handling follows [MDN's documented response types](https://developer.mozilla.org/en-US/docs/Web/API/Response/type).

`tests/test_offer_endpoint.py` covers exact serialized fields and signed-in browser cookies, independent concurrent accounts, all toggle dependencies, no response navigation/scripts/subresource loads, exactly-once dispatch, redirect isolation, unsupported fallback, HTTP errors, sign-in/challenges, missing or oversized responses, cancellation and timeout. Existing group API/UI tests cover default-off behavior, persistence, frozen runs and account-observation presentation on desktop and narrow layouts. All retailer requests are intercepted; no real cart or order is used for development validation.

Endpoint validation passed 158 distinct tests across endpoint/shortcut, toggle, usage, account-observation, monitor, cart removal/login recovery and lifecycle suites. JavaScript syntax, Python compilation and `git diff --check` passed. The only test warning was the existing Starlette/httpx deprecation.

Endpoint full-cart p95 was 94.04 ms standard and 93.23 ms paced. This fixture shows about 24–25% less full-cart time than direct form navigation; it excludes initial product/account checks, task persistence, real retailer latency, checkout and order submission. It proves neither live endpoint compatibility nor almost-instant real purchases. Raw data: `artifacts/offer-shortcut/endpoint-comparison.json`.
